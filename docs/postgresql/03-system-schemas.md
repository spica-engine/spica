# Part 3: System schemas

## How to use this document

- Plan and implement only this part. Read the code from the parts under "Depends on" on master, along with their "As built" sections. Don't open the other documents in `docs/postgresql/`.
- If this part needs something a merged part doesn't provide, stop and list it under "Requests to other parts" in your plan instead of building it.
- Follow the PR breakdown. Each PR is either a behaviour-neutral refactor or new engine code, never both, and is small enough to review in one sitting.
- Existing MongoDB suites stay green. New code brings its own tests, which run on PostgreSQL in CI. Shared behaviour uses contract suites.
- After the last PR, fill in "As built".

## Purpose

Stores Spica's own records on PostgreSQL. Their shape is known at build time and never changes at runtime. A small ORM written in Spica owns their tables.

## Rules that apply

- The ORM is written in Spica. It runs on the same PostgreSQL driver as bucket-data SQL, so the two can share connections and transactions. For example, a later part saves a bucket definition and alters its table in one transaction.
- The ORM handles CRUD and lookups by key only. List endpoints with caller filters, ACL, sort and paging go through the query facade, so on PostgreSQL they work once Part 8 merges. Filter and ACL handling is built in one place.
- The interfaces in `packages/interface` are the contract for both the MongoDB and the PostgreSQL repositories.
- The API creates every system table at startup with `CREATE TABLE IF NOT EXISTS`, from the ORM's entity definitions. Creation holds a PostgreSQL advisory lock, so replicas starting together don't race on the catalog. Fresh installs and test databases get their tables this way and run no migrations.
- A change to a table's columns updates its entity definition and ships a SQL migration on Part 2's track, for installs that already have the table. The migration runs before the API starts, so the later `CREATE TABLE IF NOT EXISTS` finds the table in its final shape and does nothing. The migration and the entity definition must describe the same shape.
- Every such migration has its own test: build the previous release's table shape and data, run the migration, assert the schema and data. The track records nothing about what ran, so the migration must also be safe to run again (`IF NOT EXISTS`, `IF EXISTS`, guarded data changes), because a rollback followed by another upgrade can apply it twice. A table that is new in a release needs no migration.
- Every system table has an `id` primary key of type UUID v7. A caller may provide it, and PostgreSQL generates it with its built-in `uuidv7()` when it isn't provided. UUID v7 starts with a timestamp, so new keys land at the end of the index, and they are unique across instances, which asset and sync installs need. MongoDB ObjectIds are not supported.
- API responses use the engine's own key name: `_id` on MongoDB, `id` on PostgreSQL. The panel will adapt later, outside this plan.

## Depends on

- **Part 0 (merged):** repository interfaces, the repository provider, the engine-aware id type.
- **Part 1 (merged):** the PostgreSQL connection, the testing module, the contract test harness. The adapter binds only a placeholder `PostgresIdTypes` that throws, plus the pool and the health check. This part replaces the placeholder and binds the remaining contract tokens.
- **Part 2 (merged):** the PostgreSQL migration track, for changing tables that already exist. It runs as `root` on upgrades, before the API starts. It does not create tables for new installs or test databases. A table a migration creates is owned by `root` and has to be altered to belong to `spica` or granted to it.

## Provides

| Contract             | What later parts expect                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| In-house ORM         | Entity definitions, mapping between records and rows, basic CRUD and queries, transactions, and sharing a transaction with raw SQL. |
| System record ids    | The UUID v7 `id` key: generated by PostgreSQL when not provided, accepted when provided, and supported by the engine-aware id type and pipe. |
| ORM repositories     | The PostgreSQL implementation of every system domain's repository, bound by the provider.                   |
| System tables        | Created by the API at startup from the entity definitions, under an advisory lock. Changes to existing tables ship as migrations on Part 2's track. |

## Not this part

- Bucket data and its tables (Part 5).
- Paginated, filtered or ACL-scoped list endpoints on PostgreSQL (Part 8). Repositories handle CRUD and simple lookups only.
- Expiry of old records (Part 4).
- Change events from system tables (Part 10).

## Target architecture

### Components

| Component             | Responsibility                                                                                        |
| --------------------- | ----------------------------------------------------------------------------------------------------- |
| In-house ORM          | A small, focused library: entities, mapping, CRUD, simple queries, transactions. Nothing more.        |
| Entity definitions    | One per domain, mirroring `packages/interface`.                                                       |
| ORM repositories      | Implement each domain's repository interface on its tables.                                           |
| Table creation        | Creates each entity's table at startup if it doesn't exist, under an advisory lock.                   |
| Table migrations      | Only when a release changes a table that earlier releases created: one SQL migration with its own test. |

### Flow

1. A controller calls its service, which calls its repository.
2. On PostgreSQL, the provider has bound the ORM repository.
3. The ORM runs SQL through the shared driver and maps rows to records in the interface shape.

## What changes

- New ORM package.
- New entities, table creation and repositories per domain. Migrations only appear in the release that first changes an existing table.
- Domain suites move to `contractSuite`, or declare `mongoOnly("reason")`, as their domain is covered.

## As built


- **ORM:** `@spica-server/data-postgresql-orm` in `packages/data/postgresql/orm`, inside the `check:data-boundary` exemption for `pg`. `defineEntity` takes a table, typed columns and indexes and adds an implicit `id uuid PRIMARY KEY DEFAULT uuidv7()`. `Orm`/`Session` offer `insert`, `insertMany`, `findById/findOne/findMany`, `count`, `aggregate`, `updateById`, `updateMany`, `replaceById` (both with `returning: "before" | "after"`, using PostgreSQL 18 `RETURNING old.*`), `deleteById/deleteMany/deleteWhere/deleteAll`, `upsert` and `raw`. `Orm.transaction` hands out a `Session` over one client, so ORM calls and raw SQL share the transaction, and nested calls reuse it. No repository uses `raw`; it stays for DDL and for the bucket tables of Part 5.
- **Expressions:** conditions in `where` (`isNotNull`, `has`, `startsWith`, `gte`, `lt`, `range`, `matches`, `notMatches`, `notEquals`, and `and`/`or` over whole conditions), update expressions (`addToSet`, `pull`, `increment`, `replacePrefix`, `jsonbSet`, `jsonbMerge`, `jsonbRemove`), `set` on `upsert`, `select`, row locks (`lock: "update"` or `"update skip locked"`), ordering and `sum` aggregates by dotted property (an embedded column, or a path into a `jsonb` column), `deleteWhere` (a count instead of the deleted rows) and `lockTransaction` (a transaction-scoped advisory lock). Values and paths are bound parameters, and `select` narrows the returned type. `deleteMany`, `deleteWhere` and an upsert without a conflict property refuse to run without a condition.
- **Entity options beyond the plan:** `idProperty` (the record property of the key), `keepNull` columns, and `embedded` column groups: a nested object stored as prefixed columns (`email: {hash}` is `email_hash`), rebuilt on read, written as an object, a dotted property or `null`. Defaults are values or the `now()`/`uuidv7()` helpers, index columns can be ordered, and index predicates and `conflictWhere` are `Where` objects rendered with escaped literals, so definitions contain no SQL text. Entities have no catch-all column: every field the API accepts is a column, found by comparing the JSON schemas with the interfaces, which added `order` and `category` to `Function`, and `type` and `category` to `Bucket`. Fixed-shape objects are columns (user `email` and `phone`, `authFactor`, `signUpStrategy`, secret `value`, storage `content`, bucket `acl` and `documentSettings`, the webhook `trigger`); what stays JSONB is typed by the interfaces (`policies.statement`, `dashboards.components`, `functions.triggers`, `strategies.options`, `histories.changes`) or is open by nature (`configs`, `preferences.value`, `jobs.payload`, `commands`, `assets`). Bucket `properties` and `indexes` wait for Part 5.
- **Record shape:** repositories return `_id`, because the interfaces in `packages/interface` declare it and the services read it. The column is `id`. Renaming the key on the wire (`id` on PostgreSQL) is left to the result shaper, which Part 6 owns. The services keep reading `_id` for now (about 425 uses in the API); because each engine stores the key natively (`id` column, `_id` field), moving the services to a neutral accessor later needs no schema change or migration. A NULL column is omitted from the record like an absent MongoDB field, except `lastLogin`, which keeps `null`: MongoDB stores `lastLogin: undefined` as `null` and the lockout check compares `attempt > lastLogin`, which is never true for `undefined`.
- **Ids:** `PostgresIdTypes` is `UuidV7Type`: lowercase canonical uuid strings typed `string & Id`. `Id.toJSON` stays required (making it optional breaks the MongoDB adapter's build). `generate()` uses the monotonic `uuid` v7, so ids from the application and from `uuidv7()` sort together.
- **Table creation:** the adapter runs `createTables` when it creates the pool (`CREATE TABLE/INDEX IF NOT EXISTS` under a session-level `pg_advisory_lock` named `spica_system_tables`, distinct from the migration lock), before any repository exists. Tables created this way belong to the role the API connects as. No table needed a migration because all are new in this release; the first column change to an existing table adds one on Part 2's track.
- **Tables:** `identities`, `users`, `verifications`, `policies`, `apikeys`, `refresh_tokens`, `strategies`, `preferences`, `configs`, `functions`, `function_logs`, `function_assets`, `webhooks`, `webhook_logs`, `env_vars`, `secrets`, `dashboards`, `statuses`, `buckets`, `histories`, `activities`, `commands`, `jobs`, `storage_objects`, `assets`. Every repository token in the MongoDB adapter's map is bound except `BUCKET_DATA_REPOSITORY` (Part 5). The adapter also binds `RESULT_SHAPER` (passthrough), `COLLECTION_NAMES` and `ORM`.
- **Where it differs from MongoDB, on purpose:**
  - Unique violations raise `DuplicateKeyError` everywhere, including `insertMany` and API key inserts, which MongoDB reports as raw driver errors.
  - `verifications` has a partial unique index on `(user_id, strategy, purpose) WHERE NOT is_used`, so `upsertPending` is a real upsert; preferences and configs have unique `scope`/`module`.
  - Policy, function and asset `replaceById` count a replacement of an existing row as 1; MongoDB's `modifiedCount` is 0 when the document is identical.
  - Status counting is one upsert on a unique `minute`; MongoDB uses a minute-`ObjectId` upsert with a retry loop. `summarize` has no `_id: null`.
  - History and function-log ranges use `created_at`, not the time inside the `ObjectId`; histories keep the newest ten explicitly, and `document_id` is `text` because bucket key types vary (Part 5).
  - `insertAll` for storage objects is one statement, so a duplicate name fails the whole batch.
  - `profilerEntries` returns `[]`.
  - `FunctionRepository.applyMergePatch` locks the row and applies the patch's `$set`/`$unset` paths in the application, walking own properties only, so a patch key such as `__proto__` is a plain field name (as in MongoDB) and cannot reach `Object.prototype`.
  - Work done in application code instead of SQL, to revisit if it matters (Part 5 may make it cheap to move):
    - `BucketRepository.findTranslatable` and `findReferencing` read every bucket's `properties` and filter in the application; MongoDB does it with an aggregation. The bucket table is small.
    - `HistoryRepository.findSummaries` loads each history's `changes` to count them (at most ten histories per document); MongoDB counts with `$size`.
    - `HistoryRepository.updateHistories` deletes the histories of the changed bucket that end up with no changes; it does not sweep empty histories of other buckets.
- **Moved between PRs:** preferences and config shipped in the passport PR, not with the other simple records, because `IdentityModule` needs `PreferenceService` and `IdentityConfigService` to boot.
- **Login:** the API boots with `--database-type postgresql` and `/passport/identify`, lockout, verify, refresh, API keys and custom policies work (`packages/api/passport/test/login.spec.ts`, a contract suite). Functions, env vars, secrets and bucket definitions are covered at repository level only.
- **Tests:** 9 contract suites run each case on MongoDB and PostgreSQL (`packages/data/postgresql/test/contract/*`, plus `login.spec.ts`), with a shared module per suite and tables cleared between cases. The ORM has 148 tests of its own (`packages/data/postgresql/orm/test`: SQL builders, expressions, embedded columns and PostgreSQL behaviour), and `packages/data/postgresql/test/helpers.spec.ts` covers the merge patch path helpers. Contract suites enable PostgreSQL locally only with `POSTGRES_URL` or `SPICA_CONTRACT_ENGINES=mongodb,postgresql`.
- **Repository base:** `FindableById`, `FindableAll`, `Insertable`, `Repository`, `UpdatableById`, `ReplaceableById` and `DeletableById` in `interface-data`, with the result type as a parameter because the contracts differ per domain. Operations with a documented different result (the "as it was before" updates, count-returning replaces) stay declared on their interface.
