## Purpose

Stores Spica's own records on PostgreSQL. Their shape is known at build time and never changes at runtime. A small ORM written in Spica owns their tables.

## Rules that apply

- The ORM is written in Spica. It runs on the same PostgreSQL driver as bucket-data SQL, so the two can share connections and transactions. For example, a later part saves a bucket definition and alters its table in one transaction.
- The ORM handles CRUD and lookups by key only. List endpoints with caller filters, ACL, sort and paging go through the query facade, so on PostgreSQL they work once Part 8 merges. Filter and ACL handling is built in one place.
- The interfaces in `packages/interface` are the contract for both the MongoDB and the PostgreSQL repositories.
- Every system table has an `id` primary key of type UUID v7. A caller may provide it, and PostgreSQL generates it with its built-in `uuidv7()` when it isn't provided. UUID v7 starts with a timestamp, so new keys land at the end of the index, and they are unique across instances, which asset and sync installs need. MongoDB ObjectIds are not supported.
- API responses use the engine's own key name: `_id` on MongoDB, `id` on PostgreSQL. The panel will adapt later, outside this plan.

## Provides

| Contract             | What later parts expect                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| In-house ORM         | Entity definitions, mapping between records and rows, basic CRUD and queries, transactions, and sharing a transaction with raw SQL. |
| System record ids    | The UUID v7 `id` key: generated by PostgreSQL when not provided, accepted when provided, and supported by the engine-aware id type and pipe. |
| ORM repositories     | The PostgreSQL implementation of every system domain's repository, bound by the provider.                   |
| System tables        | Created by migrations on the PostgreSQL track.                                                               |

## Not this part

- Bucket data and its tables (Part 5).
- Paginated, filtered or ACL-scoped list endpoints on PostgreSQL (Part 8). Repositories handle CRUD and simple lookups only.
- Expiry of old records (Part 4).
- Change events from system tables (Part 10).

## Scope

System domains:

- passport: identities, users, policies, API keys, refresh tokens, auth factors, verifications
- activity
- function: functions, function logs, webhooks, webhook logs
- env vars and secrets
- preferences, config, dashboards, status
- bucket definitions and bucket history
- replication commands and jobs
- storage object metadata and assets

## Target architecture

### Components

| Component             | Responsibility                                                                                        |
| --------------------- | ----------------------------------------------------------------------------------------------------- |
| In-house ORM          | A small, focused library: entities, mapping, CRUD, simple queries, transactions. Nothing more.        |
| Entity definitions    | One per domain, mirroring `packages/interface`.                                                       |
| ORM repositories      | Implement each domain's repository interface on its tables.                                           |
| Table migrations      | One SQL migration per domain group on the PostgreSQL track.                                           |

### Flow

1. A controller calls its service, which calls its repository.
2. On PostgreSQL, the provider has bound the ORM repository.
3. The ORM runs SQL through the shared driver and maps rows to records in the interface shape.

## What changes

- New ORM package.
- New entities, repositories and migrations per domain.
- Domain suites opt in to the PostgreSQL CI job as their domain is covered.

## PR breakdown

1. ORM core: entities, mapping, CRUD, transactions, sharing a transaction with raw SQL. Unit and PostgreSQL tests only, no domains.
2. The UUID v7 `id` key for system tables: generation, acceptance of a provided value, and support in the engine-aware id type and pipe.
3. Passport domains, with migrations and repositories. Login must work end to end.
4. Function domains.
5. Env vars, secrets, preferences, config, dashboards, status.
6. Bucket definitions and bucket history.
7. Activity, replication, storage metadata, assets.
8. Common repository base. With both engines implemented, extract the operations the repository interfaces repeat (`findById`, `insert`, `deleteById`, and so on) into one base interface. Each domain repository interface extends it, for example `ApiKeyRepository` and `UserRepository`. It is last so the shared shape comes from two real implementations.
